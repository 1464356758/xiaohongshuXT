# SYS-002｜R1修正规则（含R2状态/阶段澄清）

本文件原用于修复审核A/B指出的6个P1与两个顺带P2。14角色数量、主体职责、R01独占正式权限、PRODUCT/SKU/PERSONA/CONTENT LOCK、R09、R10/R11/R12、R13、四大门禁、局部返修、USER_FILE模式与SYS-001全部冻结。

> R2仅对第7节“R14 → R01发布与数据闭环”的 state / phase 表述进行精确修正，不改变R1其他已通过机制。

## 1. 正式SYS-002任务
正式任务路径：`任务/SYS-002/V1/任务.json`。
R1正式返修任务：`返修/SYS-002/V1/R1/任务.json`。
R1交付：`交付/SYS-002/V1/R1/交付.json`。
不得再使用 `formal_task_path: null`。

## 2. 商品研究时序
正式顺序：
`R02热点 + R03竞品并行 → R01写候选商品集 → R04逐候选深查 → R01从R04已研究集合中选择正式商品 → R05 PRODUCT/SKU草案 → R01批准LOCK`。

R04不可因为scope reduction被跳过。若R01最终想选的商品不在R04已研究集合内，必须先把该商品加入候选集并重新触发R04，R04完成前不得进入R05。

## 3. 并行屏障证据
每个并行角色都必须独立拥有：`role_id / task_path / delivery_path / result / task_version / input_revision / dependency_revision / completed_at / delivery_fingerprint_or_commit`。
只有正式交付路径存在、交付可回读、版本与依赖吻合，才能计入barrier COMPLETE。

修改 `required_role_ids`、依赖版本或barrier规则，必须创建新的 `barrier_revision` 和正式task revision，禁止静默删角色。

## 4. 独立幂等键
每个可执行角色任务只绑定一个 `role_id`。
统一公式：
`content_id|stage|role_id|task_version|input_revision|revision_round|dependency_revision`

因此R02、R03、R04永远不同键；R10、R11、R12永远不同键。

## 5. ASSET MANIFEST与图片版本身份证
运行时每一组图片都建立不可变版本清单：
`生产/资产清单/{CONTENT_ID}/{Vn}/M{manifest_revision}/ASSET_MANIFEST.json`

整组至少记录：`asset_manifest_id / manifest_revision / content_id / task_version / input_revision / revision_round`。
每页至少记录：`page_id / asset_id / asset_revision / source_task_version / input_revision / revision_round / fingerprint / asset_ref / status`。

图片实际内容变化时：
- `manifest_revision + 1`
- 只对变化页面 `asset_revision + 1`
- 变化页面生成新fingerprint
- 未变化页面保持原asset_id、asset_revision、fingerprint
- 老manifest不覆盖

若AI/工具能读取真实图片字节，自动计算SHA-256；GitHub图片可同时记录Git blob SHA。USER_FILE若环境不能直接给SHA，可使用平台提供的不可变附件/文件ID作为fingerprint。禁止要求用户手工计算SHA。

## 6. 三审同版硬门禁
R10、R11、R12的当前有效证据必须绑定同一个 `asset_manifest_id + manifest_revision`，并逐页引用其审核依赖范围内的 `asset_id + asset_revision + fingerprint`。

页面换图后，所有依赖该页面旧版本的审核证据自动 `STALE`，不能继续计入PASS。

只有真正受变更影响的审核需要重新执行。未受影响审核允许生成 `CARRY_FORWARD_BINDING`，但必须确定性证明其依赖范围内所有资产的asset_id、asset_revision、fingerprint完全没变；原审核记录本身保持不可变。

R12属于跨页视觉审核，页面视觉变化通常会影响整组节奏，所以默认视为受影响，除非任务能明确证明不影响其依赖范围。

R13只能读取已经由IMAGE-QA barrier共同PASS的同一manifest版本，不允许把不同manifest版本的三审结果拼在一起。

## 7. R14 → R01发布与数据闭环｜R2状态/阶段精确规则
正式状态-阶段映射唯一真源：`系统/生产架构/SYS-002/STATE_PHASE_TRANSITION_TABLE.json`。

强制区分：
- `state` 只能使用合法主状态，例如 READY / BUILDING / PASS / LOCKED / NEXT_TASK。
- `phase` 才描述业务阶段，例如 PUBLISH_PREP / PUBLISH_READY / PUBLISHED / DATA_WAITING / DATA_FEEDBACK / DATA_REVIEWED / NEXT_CONTENT / CLOSED。
- `PUBLISHED`、`DATA_FEEDBACK`、`CLOSED` 永远禁止写成state值。
- 每次尾段迁移必须同时记录 `state_transition` 与 `phase_transition`。
- R14只提交产物，不写state，也不写phase；所有正式state/phase迁移都由R01确认。

### 发布阶段
1. R01在CONTENT LOCK后进入发布准备：
   - `state_transition: PASS -> BUILDING`
   - `phase_transition: FINAL_APPROVAL -> PUBLISH_PREP`
2. R14生成发布包后，R01确认发布包有效：
   - `state_transition: BUILDING -> READY`
   - `phase_transition: PUBLISH_PREP -> PUBLISH_READY`
3. 用户实际发布，R14提交有效发布回执，R01确认：
   - `state_transition: READY -> PASS`
   - `phase_transition: PUBLISH_READY -> PUBLISHED`

### 数据阶段
4. 当前CONTENT需要进入数据采集时，由R01进入等待：
   - `state_transition: PASS -> READY`
   - `phase_transition: PUBLISHED -> DATA_WAITING`
5. R14按用户提供/可验证真实后台数据记录24h/72h/7d窗口，窗口状态只允许 `DUE / RECORDED / MISSED`。普通聊天模式不会自动在未来醒来；没有外部自动化时，由用户到点后再次触发R14。
6. R14提交有效数据交付，R01确认进入分析：
   - `state_transition: READY -> BUILDING`
   - `phase_transition: DATA_WAITING -> DATA_FEEDBACK`
7. R14完成数据分析/反馈报告，R01确认：
   - `state_transition: BUILDING -> PASS`
   - `phase_transition: DATA_FEEDBACK -> DATA_REVIEWED`
8. 之后仅由R01二选一：
   - 下一篇：`state_transition: PASS -> NEXT_TASK` + `phase_transition: DATA_REVIEWED -> NEXT_CONTENT`
   - 当前CONTENT结束：`state_transition: PASS -> LOCKED` + `phase_transition: DATA_REVIEWED -> CLOSED`

禁止使用 `state_transition: -> PUBLISHED`、`state_transition: -> DATA_FEEDBACK`、`state_transition: -> CLOSED`。

## 8. 本轮复审范围
R1时审核A复审：正式任务、并行证据、幂等键、R14→R01状态闭环；审核B复审：商品研究时序、ASSET MANIFEST、三审同版图片机制。

R2只交【AI系统审核员A】极小范围复审：state / phase拆分、迁移表、生产尾段是否仍存在非法state组合。
