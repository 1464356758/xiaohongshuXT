# SYS-002｜14角色生产工作流总架构 V1

> 性质：生产系统架构草案，由【AI系统制作员】根据总监在当前会话下发的 SYS-002 方向制作。由于 GitHub 当前尚无正式 `任务/SYS-002/...` 文件，本文件不得被解释为总监正式任务、SYSTEM PASS 或正式生产启用许可。

## 0. 架构目标

把现有4个AI固定为【系统建设组】，只负责设计、制作、审核、返修系统；未来真实小红书内容生产改由14个专业生产角色执行，另保留2个条件角色。

核心目标：
1. 图片系统为最高重点之一。
2. 商品、SKU、人物身份必须有独立硬门禁。
3. 研究、策划、文案、视觉、图片、审核、发布、数据形成闭环。
4. 用户操作尽量压缩为：给需求/必要素材 → 按提示切换角色 → 必要时做决定 → 最终发布/回传真实数据。
5. GitHub保存文字真源、任务、状态、LOCK、研究、审核与交付；图片允许用户直接文件传递，不强制上传GitHub。
6. 所有正式任务、正式状态、LOCK批准、跨角色返修范围和最终发布许可归【01 运营总监AI】。

# 1. 两套团队严格隔离

## 1.1 系统建设组（4角色）

只建设系统，不直接承担日常内容生产：
- AI系统总监
- AI系统制作员
- AI系统审核员A
- AI系统审核员B

建设组继续使用当前根级系统建设上下文，如：`数据库入口.json`、`当前进度.json`、`任务/SYS-*`、`交付/SYS-*`。

## 1.2 内容生产组（14+2角色）

生产运行使用独立命名空间 `生产/`，禁止把日常 CONTENT 任务状态写进系统建设组的根级 `当前进度.json`。

生产角色每轮读取顺序：
`生产/数据库入口.json → 生产/当前进度.json → active_task_path → 任务声明的输入/LOCK → 本角色规则`。

这样系统升级和内容生产可以并存，不会互相覆盖当前状态。

# 2. 14个常驻生产角色

## 01 运营总监AI
职责：总调度、创建正式CONTENT任务、汇总并行研究、决定选题/商品、批准LOCK、发布返修任务、控制状态、最终验收、创建CONTENT LOCK、指定下一角色。

可读：生产区全部正式文字资料和用户本轮提供图片。
可写：`生产/任务/`、`生产/当前进度.json`、`生产/批准/`、`生产/返修/`、`生产/产物/总监/`。
禁止：代替专业角色伪造其研究/审核；在审核FAIL时直接强行LOCK。
唯一权限：正式任务、主状态、active指针、LOCK批准、跨角色返修范围、下一阶段。

## 02 热点侦察AI
职责：找近期热点、新品/新色/联名/限定、节日/季节、美妆/美甲/护肤趋势、热门妆容/审美、争议、评论高频问题；记录时间有效性。
输入：总监任务、账号定位、历史数据（有则读）。
输出：`生产/产物/热点研究/{CONTENT_ID}/{Vn}/`。
禁止：自己决定最终商品、自己建立正式LOCK、把过期热点冒充近期热点。

## 03 市场与竞品研究AI
职责：拆热门笔记、竞品账号打法、标题/首图、页序、人物/产品比例、构图、收藏点、评论需求、同质化风险、可差异化空间。
输出：`生产/产物/竞品研究/{CONTENT_ID}/{Vn}/`。
禁止：把同行内容直接复制成成品；越权决定最终发布版本。

## 04 商品事实研究AI
职责：查官方资料、商品页、电商页、淘宝/天猫公开评价、买家秀、公开测评、优缺点、争议、不同用户意见；区分事实/用户反馈/无法确认项。
输出：`生产/产物/商品事实/{CONTENT_ID}/{Vn}/`。
禁止：把公开反馈写成账号主人的亲测；无法确认的SKU/效果不得补猜。

## 05 商品与SKU管理员AI
职责：根据04及官方/电商证据制作 PRODUCT LOCK / SKU LOCK 草案，特别处理“一链接多SKU”。
输出：`生产/产物/锁定草案/{CONTENT_ID}/{Vn}/PRODUCT_DRAFT.json`、`SKU_DRAFT.json`。
必须锁：品牌、系列、正式名、型号/款式、SKU、色号、容量/尺寸、包装版本、盘面/结构、颜色特征、官方/电商链接、参考图、同链接兄弟SKU、禁止混淆项。
禁止：证据不足时猜SKU；自己把草案写成正式批准LOCK。
批准者：仅01运营总监。

## 06 选题策划AI
职责：把热点、商品、账号定位、竞品差异和历史数据组合成值得发的一篇内容；定义核心价值、目标读者、页面逻辑和非同质化角度。
前置：PRODUCT/SKU已由总监批准，或任务明确是非具体商品型内容。
输出：`生产/产物/策划/{CONTENT_ID}/{Vn}/`。
禁止：更换已LOCK商品/SKU；擅自发明亲测结论。

## 07 文案脚本AI
职责：标题、正文、逐页文字、标签候选；强调口语、人味、信息密度、自然分享感。
前置：策划通过；读取PRODUCT/SKU锁。
输出：`生产/产物/文案/{CONTENT_ID}/{Vn}/`。
禁止：在公开成品中塞生产后台说明；也禁止虚构“我用了7天/我回购/实测10小时”等不存在的个人经历。

## 08 视觉总策划AI
职责：决定整组图的视觉故事、人物页/产品页比例、每页目的、造型、场景、构图、镜头、节奏，并生成逐页图片任务。
输出：`生产/产物/视觉策划/{CONTENT_ID}/{Vn}/`、`生产/产物/图片任务/{CONTENT_ID}/{Vn}/`。
每页任务至少写：页面编号、目的、类型、主体、persona_required、PERSONA LOCK、PRODUCT LOCK、SKU LOCK、服装、发型、妆容、首饰、表情、动作、景别、镜头、构图、背景、光线、产品位置/朝向、页面文字、字体层级、信息层级、留白、安全区、参考图、禁止项、验收点。
禁止：强迫每页都有人；擅自改已锁商品/SKU/人物身份。

### PERSONA的一次性建立
不额外增加第15角色。用户提供人物参考后：08制作PERSONA草案/锚点说明 → 11独立核验 → 01批准PERSONA LOCK。后续日常内容只读已批准PERSONA LOCK。

## 09 图片制作AI
职责：严格按逐页任务生成/制作图片，一页一页执行；只负责执行，不兼任审核。
文字输出：`生产/产物/图片执行/{CONTENT_ID}/{Vn}/执行清单.json`。
图片传递：允许 `USER_FILE`；若不进GitHub，执行清单必须记录 page_id、asset_transport、asset_ref/文件标识、对应任务版本。
禁止：自己换SKU、换产品、换人物身份、改页面核心目标；不得自称审核PASS。

## 10 商品图片核验AI
职责：只判断“图中商品是不是锁定的目标PRODUCT/SKU”。
检查：品牌、系列、包装、版本、SKU/色号、盘面/格数、颜色、Logo、文字、瓶身/盖子/配件、禁止混淆对象。
输出：`生产/审核/{CONTENT_ID}/{Vn}/商品核验/`。
必须：`independent_from_generator=true`，记录reviewer和reference_images_used。
结果：PASS / FAIL / BLOCKED。
禁止：因画面好看而放过商品错误。

## 11 人物一致性审核AI
职责：只判断“人物是不是PERSONA LOCK里的同一个女生”。
检查：脸型、五官比例、眼鼻嘴特征、识别点、正脸/45度/半身锚点、发型变化、妆容变化、局部换脸、多页身份漂移。
输出：`生产/审核/{CONTENT_ID}/{Vn}/人物一致性/`。
结果：PASS / FAIL / BLOCKED。
禁止：因发型/衣服变化就误判换人；也不得因整体相似而放过明显五官漂移。

## 12 图片终审AI
职责：整组视觉质量与跨页节奏终审。
检查：姿势、发型/服装重复、背景、镜头、构图、景别、人物页比例、产品页比例、主次、信息密度、字体层级、留白、手指/肢体、文字乱码、产品融合、背景异常、风格一致但机械复制等。
输出：`生产/审核/{CONTENT_ID}/{Vn}/图片终审/`。
结果：PASS / FAIL / BLOCKED。
原则：同一人物、同一账号风格可以一致，但视觉状态必须自然变化。

## 13 内容与真实性审核AI
职责：在三道图片检查完成后，综合核对最终文案事实、商品事实、图文对应、虚构个人经历、品牌/产品名称、效果性主张和发布风险。
输出：`生产/审核/{CONTENT_ID}/{Vn}/内容真实性/`。
结果：PASS / FAIL / BLOCKED。
禁止：代总监建立CONTENT LOCK。

## 14 发布与数据运营AI
职责：在CONTENT LOCK之后组发布包，给页序/标题/正文/标签/发布时间建议/评论运营提示；发布后记录真实24h/72h/7d数据并生成反馈。
输出：`生产/发布包/{CONTENT_ID}/{Vn}/`、`生产/数据/快照/{CONTENT_ID}/`、`生产/数据/报告/{CONTENT_ID}/`。
数据：曝光（有则记）、阅读/播放、赞、藏、评、分享、归因关注、粉丝净增、实际投流花费（有则记）。
禁止：缺数据时补0或猜数据；未CONTENT LOCK不得生成“可发布”状态。

# 3. 两个条件角色

## C1 增长投放AI
默认不运行。必须同时满足：
1. 有有效CONTENT LOCK；
2. 有真实自然数据基线；
3. 当前平台投放资格/最低金额等已核实；
4. 用户明确批准本轮预算、对象、目标。

只写：`生产/产物/投放/`、`生产/数据/投放/`。
缺任一条件：BLOCKED，不启动。

## C2 商务合作AI
默认不运行。仅在真实品牌询价、brief、报价、合同、授权、结案、回款或总监正式商务任务时启动。
只写：`生产/产物/商务/`、`生产/财务/脱敏/`。
不主动伪造品牌合作、历史合作或报价依据。

# 4. 完整生产流程与并行关系

## 阶段0：账号/人物基础
用户提供账号定位与PERSONA参考（首次或变更时）
→ 08制作PERSONA草案
→ 11独立核验
→ 01批准PERSONA LOCK
→ 写入 `active_persona_lock_path`。

日常内容若已有有效PERSONA LOCK，直接复用，不重复建人。

## 阶段1：发现机会（三路并行）
01创建CONTENT任务
→ 并行启动：02热点侦察 + 03市场竞品 + 04商品事实
→ 三路都完成后01汇总。

并行组 `DISCOVERY-G1` 的完成条件：需要的成员全部交付，任何成员BLOCKED由01决定等待、补任务或缩小范围；禁止某一角色私自代表另两路完成。

## 阶段2：商品彻底锁定（串行硬门禁）
01选择候选商品
→ 05建立PRODUCT/SKU草案
→ 证据不足：BLOCKED_SKU_UNCERTAIN / BLOCKED_PRODUCT_UNCERTAIN，01最小范围回派04或05
→ 01批准 PRODUCT LOCK + SKU LOCK
→ 更新生产当前进度唯一指针。

没有锁定目标SKU，不得进入商品型文案/图片生产。

## 阶段3：内容（串行）
06选题策划
→ 01阶段放行（只确认方向，不建立CONTENT LOCK）
→ 07文案脚本
→ 进入视觉。

## 阶段4：图片策划与制作（串行）
08整组视觉策划 + 逐页图片任务
→ 09逐页制作
→ 图片资产通过用户文件或GitHub可选方式传递。

## 阶段5：三道图片检查站（三路并行）
09完成同一图片版本后，同时交：
- 10商品图片核验
- 11人物一致性审核
- 12图片终审

并行组 `IMAGE-QA-G1` 必须三项都PASS才可进入13。
任一FAIL：01创建局部返修任务。
任一BLOCKED：进入对应BLOCKED状态，不可把另外两项PASS当成整体PASS。

## 阶段6：内容与真实性终审
三道图片检查全部PASS
→ 13综合审核最终文案 + 最终图片 + PRODUCT/SKU/PERSONA LOCK
→ PASS后交01。

## 阶段7：总监最终验收与CONTENT LOCK
01确认发布前四大门禁：
1. PRODUCT/SKU 图片核验 PASS
2. PERSONA一致性 PASS（无人物页时按模板完成NOT_APPLICABLE/合规PASS）
3. 图片质量/跨页视觉 PASS
4. 内容与真实性 PASS

四项同时满足
→ 01建立 CONTENT LOCK
→ 更新 `active_content_lock_path`
→ 交14。

## 阶段8：发布与数据反馈
14生成发布包
→ 用户实际发布（或未来有明确授权工具时按授权执行）
→ 14记录发布回执
→ 24h / 72h / 7d真实数据
→ 形成反馈摘要
→ 下一篇时供01、02、03、06读取。

# 7. LOCK体系

## PRODUCT LOCK
锁定产品身份，不等于具体SKU。

## SKU LOCK
锁定本篇具体色号/款式/版本。一个链接多个选项时必须逐项区分。

## PERSONA LOCK
锁人物身份核心锚点。允许发型、衣服、妆容、首饰、表情、姿势、场景变化；禁止换脸和核心五官漂移。

## CONTENT LOCK
仅在最终四大门禁全部PASS后由01创建，锁定：
- 最终标题/正文/逐页文字
- 最终页序
- 最终图片资产引用/文件标识
- 对应PRODUCT/SKU/PERSONA LOCK
- 四大审核结果路径
- input_revision / content_version

所有LOCK只允许01批准；其他角色只能产出草案或审核证据。

# 8. 返修与局部冻结

原则：错哪改哪。

例：P1/P2/P4/P5/P6 PASS，P3商品错误：
- 01创建 `生产/返修/{TASK_ID}/{Vn}/R1/任务.json`
- `scope=[P3]`
- `frozen_pages=[P1,P2,P4,P5,P6]`
- 默认只回09重做P3；若根因来自视觉任务错误，则最小范围回08修P3任务后再09。
- 返修后只重审受影响门禁：商品错误通常必回10；若修改可能影响人物/整组节奏，再由01追加11/12，不机械全审。

如果13发现文案虚构经历，只回07及13复审，不重做图片。
如果SKU本身锁错，属于上游P0/P1级依赖问题，01可解除受影响下游LOCK并从05开始最小必要重跑。

同一问题最多3轮；R3仍未解决 → BLOCKED_CONFLICT，交01/用户决策。

# 9. 防重复与防旧版本误读

每个角色任务幂等键：
`content_id + task_id + task_version + input_revision + role_id + dependency_revision`

规则：
1. 同幂等键已有COMPLETE且输入未变，不重复生成新版本。
2. 用户实质改需求：`input_revision + 1`，旧任务生命周期=SUPERSEDED，创建新task_version。
3. R1/R2/R3只属于对应V，不覆盖旧V/旧R。
4. 每份交付记录输入路径、使用LOCK路径、task_version、input_revision、parent_version、revision_round。
5. 禁止根据目录中文件名最大值猜当前版本；只认当前进度指针。
6. 并行角色不能互相覆盖同一正式文件，各写自己的目录；汇总由01完成。

---

# 10. 角色交接规则

所有交接只传【正式路径/资产引用】，不要求用户手动复制整篇产物。

标准交接最少包含：
- task_id / content_id / task_version / input_revision
- from_role / to_role
- current_phase / state
- input_paths
- required_lock_paths
- image_asset_refs（如有）
- frozen_scope
- unresolved_issues
- expected_output_path
- next_on_success / next_on_fail / next_on_blocked

生产角色不得私自给其他角色发布正式返修任务；遇到缺口写BLOCKED或FAIL交01，由01路由。

# 11. 用户最少操作方案

正常一篇内容，用户原则上只做：
1. 必要时给总监方向/预算/禁区；
2. 首次提供PERSONA参考，后续复用；
3. 图片若不入GitHub，按系统提示把当前图片文件交下一图片审核角色；
4. 遇到真实歧义（例如两个SKU证据冲突）时做决定；
5. 最终实际发布；
6. 平台数据若AI无法直接读取时，提供真实后台截图/数字。

AI负责：建任务、读GitHub、找输入、版本判断、LOCK引用、状态迁移建议、审核记录、局部返修范围、交付路径。

聊天默认只输出：任务号、状态、结果、问题、下一步。

# 12. 图片资产策略

- PERSONA基础参考：用户可选择长期放GitHub `生产/资产/PERSONA/`，便于跨篇复用。
- 每篇生成图：不强制进GitHub，可直接用用户文件传递。
- 非GitHub图片必须在执行/审核记录里使用稳定的本轮 `asset_ref` + page_id + task_version，防止P3/P4顺序串掉。
- 审核者必须基于实际收到的图片，不得只看文件名/Prompt宣布PASS。

# 13. 发布前硬门禁

进入CONTENT LOCK前同时满足：
- PRODUCT/SKU图片核验 PASS
- PERSONA一致性 PASS或任务确认无人物页后的合规不适用结论
- 图片终审 PASS
- 内容与真实性审核 PASS

任何FAIL → REVISION_REQUIRED。
任何证据缺失/无法确认 → 对应BLOCKED_*。
不得用总监个人判断替代缺失的独立审核结果。

# 14. 数据反哺

14在24h/72h/7d形成同口径数据快照。下一篇启动时：
- 01读取账号近期数据摘要
- 02结合热点判断“现在热什么”
- 03结合历史表现判断“我们什么结构更适合”
- 06把热点、产品、账号自身数据合并进新选题

少量样本只做探索性观察，不把一篇爆款当永久规则。

# 15. SYS-002本轮边界

本轮只建立总架构，不创建14个正式角色Prompt，不初始化真实CONTENT任务，不改根级系统建设 `当前进度.json`，不宣布生产系统已正式启用。

后续建议在A/B双审通过并由系统总监LOCK SYS-002后，再分批建设角色指令，例如：
- SYS-003：01运营总监 + 02/03/04研究组
- SYS-004：05商品/SKU + 06/07内容组
- SYS-005：08/09图片生产组
- SYS-006：10/11/12三道图片审核
