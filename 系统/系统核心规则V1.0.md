# 小红书图文生产工作流系统核心规则 V1.0

## 1. 总目标
用于女性美妆、美甲、护肤、美容类小红书图文账号。商业路径以账号增长后承接广告/品牌合作为主，不以自营卖货为主。系统重视图片、商品准确性、人物一致性、热点时效和自然文案。

## 2. 单一真源与读取顺序
1. GitHub文字资料是跨角色唯一真源。
2. 每轮必须依次读取：`数据库入口.json` → `当前进度.json` → 当前任务 → 任务声明的固定输入/LOCK。
3. 聊天记忆不得覆盖GitHub正式文件。
4. 图片可由用户直接发送文件，不强制上传GitHub；若图片不在GitHub，任务中必须记录 `asset_transport=USER_FILE`、页码和本轮文件标识。
5. 正式任务、正式状态、LOCK批准、最终系统验收只由总监决定。

## 3. 生产总流程
用户需求
→ 总监创建唯一 task_id/task_version/input_revision
→ 热点研究（必须带检索时间、时效窗）
→ 候选产品研究
→ 选定产品并建立 PRODUCT LOCK 草案
→ 多SKU商品建立唯一 SKU LOCK 草案
→ 总监批准 PRODUCT LOCK + SKU LOCK
→ 如需人物，读取已批准 PERSONA LOCK；无人物页允许跳过人物字段但必须显式 `persona_required=false`
→ 内容策划/文案
→ 文案真实性门禁
→ 逐页图片任务（每页独立）
→ 图片生成/用户传图
→ 逐页商品图片核验 + 人物一致性核验 + 图片质量审核
→ 错页进入局部返修，其余正确页冻结
→ 重要产物进入独立双审核 A+B
→ 任一 FAIL：总监只下发明确返修范围
→ A+B 双 PASS
→ 总监最终批准并建立 CONTENT LOCK
→ 生成发布包
→ 用户发布后回传真实链接/数据（如有）
→ NEXT_TASK。

任何商品身份、SKU、人物锚点不确定时必须 `BLOCKED`，禁止猜测继续。

## 4. GitHub目录骨架
```text
/
├─ 数据库入口.json
├─ 当前进度.json
├─ 系统/
├─ 任务/{TASK_ID}/{Vn}/任务.json
├─ 模板/
│  ├─ 任务/
│  ├─ 研究/
│  ├─ 锁定/
│  ├─ 图片/
│  ├─ 审核/
│  └─ 返修/
├─ 产物/
│  ├─ 热点研究/{CONTENT_ID}/{Vn}/
│  ├─ 商品研究/{CONTENT_ID}/{Vn}/
│  ├─ 文案/{CONTENT_ID}/{Vn}/
│  └─ 图片任务/{CONTENT_ID}/{Vn}/
├─ 批准/
│  ├─ PRODUCT/{PRODUCT_ID}/LOCK-Vn.json
│  ├─ SKU/{SKU_ID}/LOCK-Vn.json
│  ├─ PERSONA/{PERSONA_ID}/LOCK-Vn.json
│  └─ CONTENT/{CONTENT_ID}/LOCK-Vn.json
├─ 审核/{TASK_ID}/{Vn}/A|B|商品核验|真实性/
├─ 返修/{TASK_ID}/{Rn}/
├─ 发布包/{CONTENT_ID}/{Vn}/
└─ 交付/{TASK_ID}/{Vn}/交付.json
```
目录可以为空，但不得通过假文件名伪装真实图片资产。

## 5. 状态机
标准状态：
- `READY`：输入齐全，可开始。
- `BUILDING`：执行中。
- `REVIEWING`：产物已提交，等待独立审核。
- `REVISION_REQUIRED`：至少一项P0/P1，等待总监下发返修。
- `PASS`：本轮审核条件满足，但未锁定。
- `LOCKED`：总监批准冻结。
- `NEXT_TASK`：已交接下一任务。

异常状态：
- `BLOCKED_INPUT_MISSING`
- `BLOCKED_PRODUCT_UNCERTAIN`
- `BLOCKED_SKU_UNCERTAIN`
- `BLOCKED_PERSONA_MISSING`
- `BLOCKED_ASSET_MISSING`
- `BLOCKED_HOT_STALE`
- `BLOCKED_CONFLICT`
- `RECOVERY_REQUIRED`

合法主迁移：READY→BUILDING→REVIEWING→PASS→LOCKED→NEXT_TASK。
审核失败：REVIEWING→REVISION_REQUIRED→BUILDING→REVIEWING。
禁止制作员从 BUILDING 直接写 LOCKED；禁止审核员直接创建正式LOCK。

## 6. 防重复、旧版误读与死循环
- 幂等键：`task_id + task_version + input_revision + role`。
- 若同幂等键已有 `result=COMPLETE` 且固定输入未变，禁止重复生成新版本，只回报既有交付。
- 输入变化必须 `input_revision + 1`，旧任务自动成为 `SUPERSEDED`。
- 新产物不得覆盖旧版本；使用 V1/V2/V3。返修同一正式版本使用 R1/R2/R3 并记录 `parent_version`。
- 正式读取只认 `当前进度.json` 指向的任务与 LOCK，不允许按“文件名最大”自行猜最新。
- 默认最多3轮同一问题返修。R3仍有同一P0/P1时进入 `BLOCKED_CONFLICT` 交总监/用户决策，禁止无限循环。

## 7. 版本与LOCK
- Vn：内容/结构发生正式迭代。
- Rn：对已明确问题的局部返修，不得扩大范围。
- LOCK-Vn：总监批准的不可随意修改版本。
- LOCK引用必须保存：对象ID、来源路径、来源版本、input_revision、关键字段摘要、批准者、批准时间。
- 修改已LOCK对象必须新建版本并显式 `supersedes`，不能覆盖原LOCK。

## 8. 热点时效门禁
热点报告必须记录 `searched_at`、`evidence_date`、`freshness_class`、`valid_until`。
建议默认：
- 突发争议/新品开售/联名：优先近7天，最长14天复核。
- 季节/妆容/审美趋势：优先近30天，超过30天需重新检索确认仍活跃。
- 节日热点：必须校验当年具体日期与提前量。
若已超过 `valid_until`，进入 `BLOCKED_HOT_STALE`，不得把旧内容标成“最近热门”。

## 9. 商品与SKU硬门禁
PRODUCT LOCK负责锁产品身份，SKU LOCK负责锁本篇具体款式。一个电商链接包含多个颜色/型号时，链接本身不构成SKU身份。
生成图片前必须同时满足：
1. PRODUCT LOCK=LOCKED。
2. 若存在多个SKU，SKU LOCK=LOCKED。
3. 参考图能区分目标SKU和禁止混淆SKU。
4. 图片任务逐页引用 lock_id。
任何一项不满足：BLOCKED。

## 10. PERSONA硬门禁
PERSONA LOCK至少保存正脸、45度、半身、细节或等价锚点描述，以及脸型、五官比例、识别特征、允许变化、禁止变化。
同一人物允许换发型、服装、妆容、首饰、姿势、表情、环境。核心身份特征不得漂移。
图片任务按页声明 `persona_required`。产品静物、局部、信息图等页面可为 false，禁止强迫每页露脸。

## 11. 图片系统，最高优先级之一
每页独立任务，不允许用一句总Prompt代替。每页至少明确：
页面编号、目的、页面类型、主体、人物开关、PERSONA LOCK、商品、PRODUCT LOCK、SKU LOCK、服装、发型、妆容、表情、动作、景别、镜头角度、构图、场景/背景、光线、产品位置、产品朝向、页面文字、字体层级、信息层级、留白、安全区域、参考图、禁止项、验收点。

推荐视觉节奏可以混合：人物、产品静物、手持、局部、眼妆/唇妆、美甲特写、桌面、梳妆台、镜子、生活场景、对比、信息图。系统不得规定所有页同一种姿势或都有人物。

## 12. 商品图片逐页核验
独立于“图片好不好看”。逐页对照任务 + PRODUCT LOCK + SKU LOCK + 参考图，检查：品牌、系列、正式名称、SKU/色号、包装版本、盘面/格数、产品颜色、Logo、可见文字、盖子/瓶身/配件、容量外观、禁止混淆对象。
结论只有：PASS / FAIL / BLOCKED。
商品身份无法确定时必须 BLOCKED，不能因画面漂亮放行。

## 13. 文案与真实性
公开成品文案应自然、口语化、有具体信息，不写成研究报告。后台证据、来源、研究过程留在GitHub，不要求把“AI制作/基于资料整理/非本人试用”等生产元信息塞进最终版面。
同时严禁把他人的体验冒充为账号主体的亲身经历。没有可验证的本人体验时，不得写“我用了三天”“我实测持妆10小时”“我回购了”等事实性第一人称经历。
可写基于可核验事实的产品信息、视觉观察、使用场景建议，以及明确不冒充亲测的编辑性判断。真实性审核必须检查每个效果性主张的证据类型和边界。

## 14. 双审核
系统建设重要产物：制作员完成→审核A与审核B独立审核→两份结果都交总监。
A关注架构、权限、状态机、版本、闭环、恢复、重复执行。
B关注真实生产翻车风险，尤其图片、商品/SKU、PERSONA、热点时效、文案真实性和用户操作。
A PASS+B PASS才进入总监最终验收；任一FAIL都不得LOCK。

## 15. 局部返修
每个页面独立状态：`OPEN/PASS/LOCKED/REVISION_REQUIRED`。
例：P1/P2/P4通过、P3错误：冻结P1/P2/P4，只创建P3返修任务。返修任务必须声明 `scope=[P3]`、`frozen_pages=[P1,P2,P4]`、`allowed_changes`、`forbidden_changes`。
复审默认只审返修范围 + 受影响依赖，不重新推倒已锁页。只有发现跨页依赖或P0系统性错误时，总监才能扩大范围。

## 16. 失败恢复
- 文件不存在：BLOCKED_INPUT_MISSING，列出精确路径。
- 商品/SKU不确定：BLOCKED_PRODUCT_UNCERTAIN / BLOCKED_SKU_UNCERTAIN。
- 人物锚点缺失：BLOCKED_PERSONA_MISSING。
- 用户未传要求的图片：BLOCKED_ASSET_MISSING。
- 审核冲突：BLOCKED_CONFLICT，交总监裁决。
- 用户中途改需求：停止旧任务，input_revision+1，旧任务SUPERSEDED。
- GitHub暂时写入失败：不得声称已保存；保留本轮待写清单，下一次先回读确认后续写。

## 17. 权限
- 总监：正式任务、当前进度、LOCK、返修范围、最终批准、下一阶段。
- 制作/生产角色：只写自己本轮产物和交付，不自批。
- 审核A/B：只写审核结果，不修改正式产物和LOCK。
- 用户：提供需求、必要图片、重大方向决策、最终发布。

## 18. 简短回复
正常聊天只保留：任务号、状态、结果、问题、下一步。详细内容进GitHub。
固定最后一行：`下一步：复制给【XXX AI】。`

## 19. 发布前硬门禁
至少满足：热点未过期、PRODUCT LOCK有效、必要时SKU LOCK有效、需要人物的页面PERSONA有效、每页图片商品核验PASS、真实性审核PASS、规定的双审核完成、总监建立CONTENT LOCK。任一硬门禁缺失，不生成可发布状态。
