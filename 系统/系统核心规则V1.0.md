# 小红书图文生产工作流系统核心规则 V1.0

> SYS-001 R1：仅修复LOCK唯一指针、状态机、V/R/input_revision、PERSONA独立审核、跨页视觉审核、商品审核独立性与发布前四大硬门禁。其余已通过模块冻结。

## 1. 总目标
用于女性美妆、美甲、护肤、美容类小红书图文账号。商业路径以账号增长后承接广告/品牌合作为主，不以自营卖货为主。系统重视图片、商品准确性、人物一致性、热点时效和自然文案。

## 2. 单一真源与读取顺序
1. GitHub文字资料是跨角色唯一真源。
2. 每轮必须依次读取：`数据库入口.json` → `当前进度.json` → 当前任务 → `当前进度.json`明确指向的有效LOCK。
3. `active_product_lock_path`、`active_sku_lock_path`、`active_persona_lock_path`、`active_content_lock_path` 是当前有效LOCK的唯一正式指针。值为 `null` 即表示当前不存在有效LOCK。
4. 禁止扫描批准目录、按文件名最大值、修改时间或LOCK编号自行猜“最新”。
5. 聊天记忆不得覆盖GitHub正式文件。
6. 图片可由用户直接发送文件，不强制上传GitHub；若图片不在GitHub，任务中必须记录 `asset_transport=USER_FILE`、页码和本轮文件标识。
7. 正式任务、正式状态、LOCK批准、最终系统验收只由总监决定。

## 3. 生产总流程
用户需求
→ 总监创建唯一 task_id/task_version/input_revision
→ 热点研究（必须带检索时间、时效窗）
→ 候选产品研究
→ 选定产品并建立 PRODUCT LOCK 草案
→ 多SKU商品建立唯一 SKU LOCK 草案
→ 总监批准 PRODUCT LOCK + SKU LOCK，并把具体LOCK路径写入当前进度唯一指针
→ 如需人物，读取当前进度指向的已批准 PERSONA LOCK；无人物页允许 `persona_required=false`
→ 内容策划/文案
→ 文案真实性审核
→ 逐页图片任务（每页独立）
→ 图片生成/用户传图
→ 独立 PRODUCT/SKU 图片核验
→ 独立 PERSONA 图片一致性审核
→ 独立图片质量 + 跨页视觉审核
→ 错页进入局部返修，其余正确页冻结
→ 重要产物进入独立双审核 A+B
→ 任一 FAIL：总监只下发明确返修范围
→ A+B 双 PASS
→ 发布前四大硬门禁全部 PASS
→ 总监最终批准并建立 CONTENT LOCK，同时更新 `active_content_lock_path`
→ 生成发布包
→ 用户发布后回传真实链接/数据（如有）
→ NEXT_TASK。

任何商品身份、SKU、人物锚点不确定时必须进入对应 `BLOCKED_*`，禁止猜测继续。

## 5. 状态机
### 5.1 合法主状态
- `READY`：输入齐全，可开始。
- `BUILDING`：执行中。
- `REVIEWING`：产物已提交，等待独立审核。
- `REVISION_REQUIRED`：已有有效输入，但产物审核失败，需要返修。
- `PASS`：本轮审核条件满足，但未锁定。
- `LOCKED`：总监批准冻结。
- `NEXT_TASK`：已交接下一任务。
- `BLOCKED_INPUT_MISSING`
- `BLOCKED_PRODUCT_UNCERTAIN`
- `BLOCKED_SKU_UNCERTAIN`
- `BLOCKED_PERSONA_MISSING`
- `BLOCKED_ASSET_MISSING`
- `BLOCKED_HOT_STALE`
- `BLOCKED_CONFLICT`

不存在 `BLOCKED_OR_REVISION_REQUIRED` 这种伪状态。失败必须按真实原因落到上述一个合法状态。

### 5.2 主迁移
`READY → BUILDING → REVIEWING → PASS → LOCKED → NEXT_TASK`

审核失败：`REVIEWING → REVISION_REQUIRED → BUILDING → REVIEWING`。
缺输入/事实无法确认/资源不足：进入对应 `BLOCKED_*`。阻塞原因解除后，只能由总监根据执行位置恢复到 `READY` 或 `BUILDING`。
禁止制作员从 BUILDING 直接写 LOCKED；禁止审核员直接创建正式LOCK。

### 5.3 SUPERSEDED不是主状态
`SUPERSEDED` 只允许写入 `task_lifecycle_status`（或等价版本生命周期字段），表示旧任务/旧输入已失效。它不得写进 `当前进度.json.state` 冒充主工作流状态。
任意时刻 `当前进度.json.state` 只能有一个值。

## 6. 防重复、旧版误读与死循环
- 幂等键：`task_id + task_version + input_revision + role`。
- 若同幂等键已有 `result=COMPLETE` 且固定输入未变，禁止重复生成新版本，只回报既有交付。
- 用户需求发生实质变化：`input_revision + 1`，必须同时生成新的 `task_version`；旧任务设置 `task_lifecycle_status=SUPERSEDED`。
- Vn代表该输入下的正式任务/产物版本；R1/R2/R3只能属于对应V，不得跨V复用。
- 返修唯一路径：`返修/{TASK_ID}/{Vn}/{Rn}/`。禁止使用 `返修/{TASK_ID}/{Rn}/`。
- 不得覆盖旧V、旧R。
- 所有交付必须记录：`task_version + input_revision + parent_version + revision_round`；首轮无返修时 `revision_round=null`。
- 正式读取只认 `当前进度.json` 指向的任务与四类LOCK指针，不允许猜最新。
- 默认最多3轮同一问题返修。R3仍有同一P0/P1时进入 `BLOCKED_CONFLICT`，禁止无限循环。

## 7. 版本与LOCK
- Vn：正式任务/输入版本。用户需求实质变化时必须新V。
- Rn：某个明确V下的局部返修。
- LOCK-Vn：总监批准的不可随意修改版本。
- LOCK引用必须保存：对象ID、来源路径、来源版本、input_revision、关键字段摘要、批准者、批准时间。
- 修改已LOCK对象必须新建版本并显式 `supersedes`，不能覆盖原LOCK。
- 新LOCK生效后，总监必须把具体文件路径写进 `当前进度.json` 对应 `active_*_lock_path`；未生效则保持 `null`。

## 8. 热点时效门禁
热点报告必须记录 `searched_at`、`evidence_date`、`freshness_class`、`valid_until`。
建议默认：突发争议/新品/联名优先近7天，最长14天复核；季节/妆容/审美趋势优先近30天；节日热点校验当年日期。超过 `valid_until` 进入 `BLOCKED_HOT_STALE`。

## 9. 商品与SKU硬门禁
PRODUCT LOCK负责锁产品身份，SKU LOCK负责锁本篇具体款式。一个电商链接包含多个颜色/型号时，链接本身不构成SKU身份。
生成图片前必须同时满足 PRODUCT LOCK=LOCKED、必要SKU LOCK=LOCKED、参考图足以区分目标SKU、图片任务逐页引用lock_id。否则进入对应BLOCKED状态。

## 10. PERSONA硬门禁
PERSONA LOCK保存正脸、45度、半身、细节或等价锚点描述，以及脸型、五官比例、识别特征、允许变化、禁止变化。
同一人物允许换发型、服装、妆容、首饰、姿势、表情、环境。核心身份特征不得漂移。图片任务按页声明 `persona_required`，不强迫每页露脸。

## 11. 图片系统，最高优先级之一
每页独立任务，不允许用一句总Prompt代替。每页至少明确：页面编号、目的、页面类型、主体、人物开关、PERSONA LOCK、商品、PRODUCT LOCK、SKU LOCK、服装、发型、妆容、表情、动作、景别、镜头角度、构图、场景/背景、光线、产品位置、产品朝向、页面文字、字体层级、信息层级、留白、安全区域、参考图、禁止项、验收点。
图片可混合人物、产品静物、手持、局部、眼妆/唇妆、美甲特写、桌面、梳妆台、镜子、生活场景、对比、信息图。

## 12. 商品图片逐页核验
必须由图片生成者之外的独立审核者执行，并记录 `reviewer`、`independent_from_generator=true`、`reference_images_used`。
逐页对照任务 + PRODUCT LOCK + SKU LOCK + 参考图，检查品牌、系列、正式名称、SKU/色号、包装版本、盘面/格数、产品颜色、Logo、可见文字、盖子/瓶身/配件、容量外观、禁止混淆对象。
结论只有 PASS / FAIL / BLOCKED。身份无法确认必须BLOCKED，不能因画面漂亮放行。

## 13. PERSONA图片一致性独立审核
必须使用独立模板，并由图片生成者之外的审核者执行。至少检查：
- 是否仍是PERSONA LOCK里的同一人；
- 脸型、五官比例、眼鼻嘴特征、标志性识别点；
- 正脸/45度/半身与参考锚点是否一致；
- 发型变化后是否仍保持同一身份；
- 妆容变化是否误改五官；
- 局部页是否出现明显换脸；
- 多页之间人物是否彼此不一致。

结果只有 PASS / FAIL / BLOCKED，并记录 reviewer、`independent_from_generator=true`、reference_images、failed_pages、required_revision_pages。若整组无人物页，可在完成“不适用核验”后以 PASS 记录理由，不得伪造人物审核素材。

## 14. 图片质量 + 跨页视觉独立审核
逐页与整组同时审核，专门拦截“每张单看没错，合起来像复制粘贴”。至少检查：姿势重复、发型重复、服装重复是否过度、背景重复、镜头重复、构图重复、景别单一、人物页比例过高、产品页比例过低、页面节奏、主次关系、信息密度、字体/文字层级、留白、图片质量异常、跨页风格一致但机械复制。
原则：同一人物、同一账号风格可以保持，但视觉状态必须自然变化。
若仅P3失败，则 `required_revision_pages=[P3]`，其余PASS页继续冻结；只有真实跨页依赖问题才能扩大最小必要返修范围。

## 15. 文案与真实性
公开成品文案应自然、口语化、有具体信息，不写成研究报告。后台证据、来源、研究过程留在GitHub，不要求把“AI制作/基于资料整理/非本人试用”等生产元信息塞进最终版面。
同时严禁把他人的体验冒充为账号主体亲身经历。没有可验证本人体验时，不得写虚假的明确第一人称试用事实。真实性审核必须检查效果性主张的证据类型和边界。

## 16. 双审核
系统建设重要产物：制作员完成→审核A与审核B独立审核→两份结果都交总监。A关注架构、权限、状态机、版本、闭环；B关注真实生产翻车风险。A PASS+B PASS才进入总监最终验收；任一FAIL都不得LOCK。

## 17. 局部返修
每页独立状态：`OPEN/PASS/LOCKED/REVISION_REQUIRED`。
例：P1/P2/P4通过、P3错误：冻结P1/P2/P4，只创建 `返修/{TASK_ID}/{Vn}/R1/` 下的P3返修任务。返修必须声明 scope、frozen_pages、allowed_changes、forbidden_changes、re_review_scope。
复审默认只审返修范围 + 受影响依赖。只有发现跨页依赖或P0系统性错误时，总监才能扩大范围。

## 18. 发布前四大硬门禁
进入最终发布CONTENT LOCK前，以下四项必须同时为 PASS：
1. `PRODUCT/SKU核验 PASS`
2. `PERSONA一致性 PASS`
3. `图片质量/跨页视觉审核 PASS`
4. `文案真实性 PASS`

任一项 FAIL：进入 `REVISION_REQUIRED`，按最小范围返修。
任一项 BLOCKED：进入对应合法 `BLOCKED_*`。
四项未全部PASS时，禁止建立最终发布CONTENT LOCK、禁止标记可发布、禁止生成最终发布包。

## 19. 失败恢复
- 文件不存在：`BLOCKED_INPUT_MISSING`，列精确路径。
- 商品/SKU不确定：`BLOCKED_PRODUCT_UNCERTAIN` / `BLOCKED_SKU_UNCERTAIN`。
- 人物锚点缺失：`BLOCKED_PERSONA_MISSING`。
- 用户未传要求图片：`BLOCKED_ASSET_MISSING`。
- 热点过期：`BLOCKED_HOT_STALE`。
- 审核意见无法裁决：`BLOCKED_CONFLICT`。
- 用户中途实质改需求：停止旧任务，旧任务lifecycle标记SUPERSEDED，input_revision+1并新建task_version。
- GitHub写入失败：不得声称已保存；下一次先回读再续写，不强覆盖新SHA。

## 20. 权限
- 总监：正式任务、当前进度主状态、LOCK、返修范围、最终批准、下一阶段。
- 制作/生产角色：只写自己本轮产物和获授权的结构修复，不自批。
- 审核A/B：只写审核结果，不修改正式产物和LOCK。
- 用户：提供需求、必要图片、重大方向决策、最终发布。

## 21. 简短回复
正常聊天只保留：任务号、状态、结果、问题、下一步。详细内容进GitHub。
固定最后一行：`下一步：复制给【XXX AI】。`
